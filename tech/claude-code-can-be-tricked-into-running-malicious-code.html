Claude Code Can Be Tricked Into Running Malicious Code

A malicious website, a poisoned Python module and a seemingly harmless request to “summarize this page” were enough to turn an AI coding assistant into an attacker-controlled execution environment.


Artificial intelligence agents are increasingly being trusted with something traditional chatbots never had: the ability to act.

They can read files, browse websites, execute shell commands, install dependencies, modify source code, run tests and launch other programs. That makes them extraordinarily useful for software development.

It also creates a new security problem.

A malicious instruction hidden inside something an AI agent is asked to process can potentially become a command executed on the user’s machine.

Security researcher Johann Rehberger, better known online as wunderwuzzi, has demonstrated a particularly striking example against Claude Code running Opus 5 in Auto Mode.

His attack begins with an almost absurdly ordinary request:

“Summarize this website.”

There is no request to install malware.

No instruction to execute a suspicious binary.

No obvious command asking Claude to compromise the computer.

Instead, the attack gradually manipulates the coding agent through a chain of individually plausible decisions until attacker-controlled code is executed.

Rehberger reported success rates between 60% and 80% across three attack variants, with each variant tested only five times. That is a tiny sample, and he explicitly cautioned that the results were not comprehensive. Nevertheless, the demonstration exposes a significant architectural problem for autonomous coding agents: a model’s ability to recognize suspicious instructions is not the same thing as securely containing what the model can execute. (SIT-CyberSecurity⁠)


The uncomfortable timing

The disclosure is particularly interesting because Anthropic had recently made Auto Mode the default for Claude Code on Pro, Max and Team plans.

Auto Mode is intended to reduce the constant permission prompts developers encounter when using an autonomous coding agent. Instead of asking the user to approve every potentially sensitive operation, Claude Code uses additional safety mechanisms to determine whether an action is consistent with the user’s intent.

Anthropic said its independent evaluation, conducted by Trajectory Labs, tested 72 indirect prompt-injection scenarios ten times each.

That produced 720 attack attempts, with no successful attacks against Opus 5, Fable 5 or Sonnet 5 running Auto Mode in that evaluation. (Claude⁠)

That sounds extremely strong.

But there is an important distinction.

A security evaluation measures performance against the scenarios included in that evaluation. Rehberger was attempting something different: constructing a new, multi-stage attack specifically designed to make apparently harmless actions eventually produce malicious behavior.

That distinction is at the heart of this incident.

A security classifier can perform perfectly against one test set and still fail against an attack technique that was not represented in that set.

And that’s precisely what makes this demonstration interesting.


It starts with a website

The first stage of Rehberger’s attack is social engineering directed at the AI rather than the human.

The user asks Claude Code to retrieve and summarize content from a website.

The website appears to contain legitimate-looking notebook or catalogue records.

Claude initially attempts to retrieve the content using its normal web-fetching mechanism.

That request fails with an HTTP 415 Unsupported Media Type response.

Instead of stopping, the agent looks for another way to retrieve the information.

It eventually uses the shell and curl.

That decision is important because the attack is not based on convincing the model to execute an obviously malicious command.

The model believes it is simply finding another way to accomplish the user’s original request.

The malicious instructions are effectively embedded in the workflow.

This is the essence of indirect prompt injection.

The attacker does not necessarily control the prompt the user types into the AI.

The attacker controls information that the AI subsequently reads.

That information can contain instructions designed to influence the agent’s behavior.


The website doesn’t deliver what it appears to

The malicious site then redirects the agent to a ZIP archive.

The archive is designed to look like a legitimate collection of notebook or catalogue data.

It contains files such as:

  • Metadata
  • A README
  • Encoded JSON notebook records
  • A decoder
  • A macOS binary
  • A Python file named struct.py

Nothing about the archive needs to scream “malware.”

That is part of the technique.

The attacker wants the AI to treat the archive as data that needs to be processed.

And Claude initially makes an important security decision correctly.

It refuses to execute the supplied decoder binary.

That should have been the end of the attack.

It wasn’t.


The safety decision becomes the attack path

Claude decides to write its own decoder instead.

On the surface, this looks like a safer choice.

Rather than executing an unfamiliar binary supplied by a website, the agent can write a small Python program to decode the data itself.

The problem is where that Python program is executed.

The malicious archive contains a file named:

struct.py

That name is not random.

struct is also the name of a legitimate Python standard-library module.

Python’s module resolution behavior can cause a local module to take precedence over the expected standard-library module when code is executed from a directory containing a file with the same name.

This technique is known as module shadowing.

The attacker therefore doesn’t necessarily need Claude to explicitly write:

import struct

The malicious module can be reached indirectly.

And that is where the attack becomes particularly interesting.


⸻


The innocent-looking 

base64

import

The decoder Claude writes needs to process encoded data.

One natural choice is Python’s built-in base64 module.

But base64 itself depends on other standard-library components, including struct.

That creates the trap.

The model believes it is importing a legitimate Python standard-library module.

Python instead finds the attacker’s local struct.py.

The local file executes.

At that moment, the attack has crossed an important boundary:

untrusted data has become executable code.

The model did not intentionally decide to execute the attacker’s Python file.

It reached the file through normal programming behavior.

This is one reason traditional prompt-injection defenses have difficulty with attacks like this.

The dangerous instruction is not necessarily expressed as a sentence such as:

“Run this malicious command.”

Instead, the malicious behavior emerges from the interaction between:

  1. The agent’s reasoning
  2. The files it downloads
  3. The directory in which it works
  4. Programming-language behavior
  5. Tool permissions
  6. Network access
  7. The agent’s willingness to execute its own generated code

The attack is therefore better understood as a chain of trust failures than as one malicious prompt.


⸻


From poisoned Python file to remote execution

According to Rehberger’s demonstration, the malicious struct.py was capable of launching a separate Python process that contacted an external command-and-control endpoint and executed a remote payload.

In the demonstration environment, the payload ultimately opened Calculator.

That detail is important.

Opening Calculator is not itself dangerous.

It is a visible proof that arbitrary code execution occurred.

A real attacker would have little reason to stop there.

Once arbitrary code execution is achieved, the potential impact depends heavily on the privileges and environment available to the coding agent.

That could include access to:

  • Source code
  • Environment variables
  • Local configuration files
  • API credentials
  • SSH keys
  • Cloud credentials
  • Developer tokens
  • Project secrets
  • Local databases
  • Browser sessions
  • Files outside the project directory
  • Network services accessible from the host

The exact impact depends on the permissions granted to the agent.

That qualification matters.

Prompt injection does not automatically mean total machine compromise.

It becomes significantly more dangerous when the compromised agent has broad filesystem access, credentials or unrestricted network connectivity.


⸻


The attack can go one level deeper

Rehberger also demonstrated another variation that is arguably more concerning.

The malicious code could launch another instance of Claude Code in non-interactive mode.

In other words, the compromised agent could effectively create another AI agent.

The child process inherited its own tool capabilities and context.

According to Rehberger, some runs resulted in basic reconnaissance commands such as:

  • whoami
  • uname
  • id

The demonstration also showed the agent opening Calculator and writing files inside the user’s home directory.

Again, these actions were performed in a controlled demonstration environment.

The significance isn’t Calculator.

It is the fact that one compromised autonomous agent can potentially become the mechanism for spawning another autonomous process.

That creates an uncomfortable recursive possibility:

An AI agent compromised through untrusted content can potentially use its own capabilities to create additional processes with additional capabilities.

This is one of the reasons agent security is fundamentally different from ordinary chatbot security.

⸻


Why Auto Mode missed it

This is where the story becomes more complicated than “Claude was hacked.”

Auto Mode is not a magic firewall.

Anthropic describes its approach as a defense-in-depth system involving model behavior, probes and an intent classifier designed to determine whether actions are consistent with the user’s request. (Claude⁠)

The problem with multi-stage attacks is that each individual step can look reasonable.

Consider the sequence from the agent’s perspective:

Step 1: Retrieve a website.

Reasonable.

Step 2: The preferred fetch mechanism fails.

Reasonable to try another retrieval method.

Step 3: Download an archive containing data.

Potentially reasonable.

Step 4: Extract the archive.

Potentially reasonable.

Step 5: Decode encoded records.

Reasonable.

Step 6: Write a decoder.

Reasonable.

Step 7: Import base64.

Completely normal Python.

Step 8: Python loads a local module with the same name as a standard-library module.

Now the security boundary has already been crossed.

The classifier may be evaluating the apparent intent of individual operations while the attacker is exploiting the composition of those operations.

That is the deeper lesson.

A dangerous result does not always require a dangerous-looking action.


⸻


The strangest part: the safety system reportedly blocked cleanup

In some runs, according to Rehberger and subsequent reporting, Claude recognized that something had gone wrong and attempted to terminate the malicious process.

The Auto Mode safety mechanism reportedly prevented the cleanup command.

That creates a particularly uncomfortable scenario.

The security mechanism allowed the chain that resulted in compromise but then interfered with the agent’s attempt to recover.

This is not evidence that Auto Mode is inherently useless.

It demonstrates a more fundamental problem with relying on a probabilistic classifier as the primary security boundary.

A classifier can make mistakes in both directions.

It can:

  • Allow something dangerous.
  • Block something safe.
  • Misunderstand the relationship between two individually benign operations.
  • Fail to understand an attack that depends on several stages.
  • Prevent recovery after detecting a compromise.

That is why containment must exist underneath the model-level safety system.


⸻


Anthropic’s own security research points to the same conclusion

Interestingly, this is not a lesson Anthropic itself disputes.

Anthropic has published extensive material on sandboxing Claude Code.

The company’s security architecture emphasizes two critical containment boundaries:

1. Filesystem isolation

The agent should only be able to access files it actually needs.

If an attacker compromises the agent, the attacker should not automatically inherit access to the user’s entire home directory.

2. Network isolation

The agent should not have unrestricted outbound Internet access.

This matters because a compromised process can otherwise communicate with attacker-controlled infrastructure or exfiltrate sensitive information.

Anthropic explicitly states that effective containment requires both filesystem and network isolation. (Anthropic⁠)

This is a critical point.

If you sandbox the filesystem but allow unrestricted networking, a compromised agent may still steal data.

If you restrict networking but give the agent broad filesystem access, malicious code may still access credentials and sensitive files.

The two controls reinforce each other.


⸻


The real security boundary isn’t the model

This incident highlights a principle that developers building AI agents need to understand:

Never treat the model as the security boundary.

A language model can reason about security.

It can recognize suspicious instructions.

It can refuse malicious requests.

It can analyze malware.

It can even detect that it has been compromised.

But none of those capabilities turn the model into an operating-system security boundary.

Models are probabilistic systems.

Operating systems can enforce permissions.

That distinction matters.

If Claude is running inside an environment where it cannot access your SSH keys, cannot read your personal files and cannot connect to arbitrary Internet hosts, a successful prompt injection can be dramatically less damaging.

If the same agent is running with unrestricted access to the developer’s machine, the stakes are much higher.


⸻


What developers should actually do

The lesson is not “stop using AI coding agents.”

The lesson is to deploy them like untrusted automation.

Run agents inside a sandbox

Use an isolated container, VM or operating-system sandbox where practical.

The goal is to ensure that a compromised agent cannot freely move into the rest of the machine.

Anthropic’s own Claude Code sandboxing architecture uses operating-system-level controls to enforce filesystem and network boundaries. (Anthropic⁠)

Restrict filesystem access

Give the agent access to the project it needs.

Do not automatically expose:

~/.ssh
~/.aws
~/.config
.env
password stores
browser profiles
private keys


or other sensitive locations.

Restrict network egress

A compromised agent should not automatically be able to connect to every server on the Internet.

Allow only the domains and services genuinely required for the development workflow.

Keep secrets outside the agent’s environment

Do not assume that because the model is “trusted” with your code, it should also be trusted with every credential on the machine.

Separate credentials by privilege.

Prefer short-lived, scoped credentials wherever possible.

Treat downloaded archives as hostile

ZIP files, repositories, documentation, packages and websites can all carry executable content.

The fact that something looks like data does not make it trustworthy.

Be especially careful with generated code

“Claude wrote it” is not a security property.

Generated code can execute:

  • imports
  • shell commands
  • package installers
  • subprocesses
  • network requests
  • scripts

The code still needs to be treated like code written by an unknown developer.

Avoid broad autonomous permissions on sensitive machines

A development agent running inside a disposable environment is one thing.

The same agent running with access to production credentials is another.

The blast radius is determined by the environment.


The bigger problem: agents blur the line between data and instructions

Traditional software generally has a clear distinction between data and commands.

A text file is data.

A shell command is an instruction.

An AI agent complicates that distinction.

The agent reads the text and decides what to do with it.

That means an attacker can put instructions inside:

  • Websites
  • GitHub issues
  • README files
  • Documentation
  • PDFs
  • Emails
  • Source comments
  • Package metadata
  • Search results
  • API responses
  • Database records

The AI may treat those instructions as part of the context it uses to decide what to do next.

That is the fundamental challenge of indirect prompt injection.

The attacker does not need to control the user’s prompt.

They only need to control something the agent will eventually read.


This is bigger than Claude

It would be a mistake to frame this exclusively as an Anthropic problem.

The same architectural issue applies to virtually every agent capable of:

  • browsing
  • executing code
  • reading arbitrary documents
  • accessing local files
  • calling APIs
  • running shell commands
  • installing software
  • modifying repositories
  • spawning processes

The underlying problem is not the brand of model.

It is the combination of:

untrusted input + autonomous reasoning + powerful tools + insufficient containment.

As AI agents become more capable, that combination becomes increasingly important.


A useful way to think about agent security

There are effectively three layers.

Layer 1 — Model alignment

The model should understand that malicious instructions are untrusted.

This is useful.

But it is not enough.

Layer 2 — Action supervision

A classifier, approval system or policy engine should determine whether an action is allowed.

Also useful.

Still not enough.

Layer 3 — Hard containment

The operating environment should physically prevent the agent from accessing things it should never be able to reach.

This is the layer that limits the blast radius when Layers 1 and 2 fail.

The strongest architecture uses all three.

The weakest assumes Layer 1 will never fail.


The uncomfortable conclusion

Rehberger’s demonstration does not prove that Claude Code is universally insecure.

It does demonstrate something more important.

A determined attacker can construct multi-stage prompt-injection chains that exploit the gap between what an AI agent thinks it is doing and what the underlying operating environment actually allows it to do.

The reported 60–80% success rate came from a very small sample, so it should not be interpreted as a universal probability that “Claude will be hacked 80% of the time.” (SIT-CyberSecurity⁠)

Likewise, Anthropic’s 0% result from its separate 720-attempt evaluation should not be interpreted as proof that Auto Mode can never be bypassed. (Claude⁠)

Both findings illustrate the same reality:

Security evaluations are measurements, not guarantees.

The most important takeaway is therefore much simpler.

Don’t ask only:

“Can the AI recognize the attack?”

Ask:

“If the AI fails to recognize the attack, what can the attacker actually reach?”

That is the difference between a prompt-injection bug and a catastrophic compromise.

AI agents are going to become more autonomous.

They will browse for us.

They will write code for us.

They will execute commands for us.

They will install software for us.

Eventually, they will operate entire development environments with minimal human supervision.

The more authority we give them, the less acceptable it becomes to rely on the model itself as the last line of defense.

Treat the agent as untrusted. Sandbox it. Restrict its filesystem. Restrict its network. Limit its credentials. Assume that eventually, something will fool it.

Because the strongest security boundary is not the model saying:

“I won’t do that.”

It is the operating system making sure that, even if the model does, there isn’t much it can damage.
