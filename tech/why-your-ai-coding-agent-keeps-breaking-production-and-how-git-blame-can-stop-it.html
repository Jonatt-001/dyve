<article class="article-content">




 <p>AI coding agents are getting remarkably good at writing software.</p>


 <p>They can inspect a repository, understand a task, modify multiple files, run tests, fix errors, open pull requests, and sometimes work through an entire feature with surprisingly little human intervention.</p>


 <p>For developers using tools such as Claude Code, Cursor, Windsurf, GitHub Copilot, and other AI coding systems, this can feel like having another engineer sitting beside you.</p>


 <p>And that is exactly where the problem begins.</p>


 <p>Because there is one thing your AI coding agent can understand extremely well but still misunderstand:</p>


 <blockquote>

  <p><strong>The code that already exists.</strong></p>

 </blockquote>


 <p>An AI agent can look at a function and understand what it appears to do.</p>


 <p>It can identify duplicated logic. It can recognize an old-looking API. It can spot a strange <code>setTimeout()</code>. It can see a retry value of <code>7</code> and decide that <code>3</code> looks more reasonable.</p>


 <p>It can replace a complicated block with a cleaner abstraction.</p>


 <p>It can make the code look better.</p>


 <p>It can make the tests pass.</p>


 <p>And it can still break production.</p>


 <p>That is not necessarily because the model is "bad at coding."</p>


 <p>The deeper problem is <strong>missing historical context</strong>.</p>


 <p>The code in front of an AI agent is the final result of hundreds of decisions made by developers, production incidents, customer complaints, infrastructure limitations, third-party API behaviour, browser bugs, rushed releases, and lessons learned the hard way.</p>


 <p>That history is often not written in the code.</p>


 <p>It is written in Git.</p>


 <p>And that makes commands such as <code>git blame</code> and <code>git log -L</code> surprisingly powerful tools for AI-assisted software engineering.</p>



 <h2>AI Coding Agents Have a Context Problem</h2>


 <p>There is an important distinction between <strong>understanding code</strong> and <strong>understanding why the code exists</strong>.</p>


 <p>An LLM can look at this:</p>


 <pre><code>MAX_RETRIES = 7</code></pre>


 <p>and understand what it means.</p>


 <p>But it cannot automatically know why the number is <code>7</code>.</p>


 <p>Maybe the original developer chose it randomly.</p>


 <p>Maybe it came from an old Stack Overflow answer.</p>


 <p>Or maybe, two years ago, a payment provider started returning intermittent gateway errors and somebody increased the retry window after a production incident.</p>


 <p>Those two situations look identical in the current source code.</p>


 <p><strong>The history is what separates them.</strong></p>


 <p>This matters even more now because AI-assisted development is becoming normal. Developers are increasingly using AI tools to write, review, debug, refactor, and maintain software.</p>


 <p>The productivity gains are real.</p>


 <p>But increased coding velocity creates another problem:</p>


 <blockquote>

  <p><strong>There is now more code being changed, and it can be changed faster than humans can fully understand it.</strong></p>

 </blockquote>


 <p>That makes software history increasingly important.</p>



 <h2>The Real Problem: AI Sees the Code, but Not the Battle Scars</h2>


 <p>Most software systems contain code that looks strange for a reason.</p>


 <p>Some of it is genuinely bad code.</p>


 <p>Some of it is technical debt.</p>


 <p>And some of it is what engineers might call <strong>load-bearing legacy code</strong>.</p>


 <p>That last category is dangerous.</p>


 <p>It is code that looks unnecessary until you remove it.</p>


 <p>Then everything falls apart.</p>


 <p>A useful mental model is <strong>Chesterton's Fence</strong>:</p>


 <blockquote>

  <p>Before removing something that looks unnecessary, understand why it was put there.</p>

 </blockquote>


 <p>Imagine an AI agent encounters this:</p>


 <pre><code>setTimeout(() =&gt; {

  initializeWidget();

}, 0);</code></pre>


 <p>The agent may reasonably think:</p>


 <blockquote>

  <p>"Why delay this by one event-loop tick? I can call <code>initializeWidget()</code> directly."</p>

 </blockquote>


 <p>From a purely local perspective, that may look like a legitimate improvement.</p>


 <p>But perhaps that delay was introduced after a browser rendering race.</p>


 <p>Perhaps a DOM node must exist before initialization.</p>


 <p>Perhaps another callback has to finish first.</p>


 <p>Perhaps a third-party library mutates the DOM during the current task.</p>


 <p>Perhaps somebody spent hours debugging a problem that only appeared on certain Android devices.</p>


 <p>The source code does not necessarily tell the story.</p>


 <p><strong>The Git history might.</strong></p>



 <h2>Why This Matters for Nigerian Developers</h2>


 <p>This problem becomes especially practical when you are building software for Nigerian users and businesses.</p>


 <p>Generic engineering advice does not always account for the conditions a real application has to survive.</p>


 <p>A Nigerian fintech application, for example, may have to deal with:</p>


 <ul>

  <li>Payment-provider retries</li>

  <li>Intermittent network connections</li>

  <li>Webhook delays</li>

  <li>Inconsistent third-party responses</li>

  <li>Mobile-first traffic</li>

  <li>Low-bandwidth users</li>

  <li>Infrastructure cost constraints</li>

  <li>SMS delivery delays</li>

  <li>Authentication edge cases</li>

  <li>Asynchronous payment confirmation</li>

  <li>Bank and payment-gateway response variations</li>

 </ul>


 <p>An e-commerce platform can have a completely different collection of problems:</p>


 <ul>

  <li>Customers switching between WhatsApp and the website</li>

  <li>Payment confirmation arriving after checkout</li>

  <li>Inventory changing between checkout and payment</li>

  <li>Users refreshing pages repeatedly</li>

  <li>Unstable client networks</li>

  <li>Large image traffic from mobile devices</li>

  <li>Third-party delivery integrations</li>

 </ul>


 <p>And many Nigerian startups operate with very small engineering teams.</p>


 <p>One developer might have built the original system. Another developer takes over six months later. Then an AI coding agent is introduced.</p>


 <p>The original developer may be unavailable.</p>


 <p>The Slack conversation may be gone.</p>


 <p>The Jira ticket may be archived.</p>


 <p>The documentation may never have been written.</p>


 <p>But the Git commit can still be there.</p>


 <p>That is why Git history is more than version control.</p>


 <p><strong>It is institutional memory.</strong></p>



 <h2>Three Ways an AI Refactor Can Quietly Break Production</h2>


 <h3>1. The "Unnecessary" Delay</h3>


 <p>Suppose an AI agent sees:</p>


 <pre><code>setTimeout(() =&gt; {

  refreshLayout();

}, 0);</code></pre>


 <p>It removes the timeout because calling the function directly appears simpler.</p>


 <p>The unit tests pass.</p>


 <p>The linter passes.</p>


 <p>The code review looks cleaner.</p>


 <p>Then a production-only UI race appears.</p>


 <p>Maybe it happens only on a particular browser.</p>


 <p>Maybe only on slower devices.</p>


 <p>Maybe only when network data arrives at exactly the wrong moment.</p>


 <p>The agent did not introduce a syntax error.</p>


 <p>It introduced a <strong>context error</strong>.</p>



 <h3>2. The Magic-Number Cleanup</h3>


 <p>Consider:</p>


 <pre><code>max_retries = 7</code></pre>


 <p>An AI agent may see <code>7</code> and think:</p>


 <blockquote>

  <p>"Three retries is more conventional."</p>

 </blockquote>


 <p>It changes the value:</p>


 <pre><code>max_retries = 3</code></pre>


 <p>The application still starts.</p>


 <p>The tests still pass.</p>


 <p>Nothing looks obviously broken.</p>


 <p>Then an external service becomes temporarily unavailable.</p>


 <p>The application retries three times, gives up, and drops an operation that previously had enough time to recover.</p>


 <p>If that operation happens to be a payment webhook, background job, notification, or synchronization process, the consequences can be much larger than the code change suggests.</p>


 <p>The number was not necessarily "magic."</p>


 <p>It was undocumented operational knowledge.</p>



 <h3>3. The Duplicated Validation Check</h3>


 <p>An AI notices:</p>


 <pre><code>if (!user) {

  return;

}


await loadUserData();


if (!user) {

  return;

}</code></pre>


 <p>The second check looks redundant.</p>


 <p>So the agent removes it.</p>


 <p>That might be perfectly safe.</p>


 <p>Or it might not.</p>


 <p>If <code>loadUserData()</code> changes state asynchronously, invokes another service, or creates a race between two execution paths, the second validation may exist because somebody previously discovered a failure mode.</p>


 <p>Again, the important question is not:</p>


 <blockquote>

  <p>"Does this code look redundant?"</p>

 </blockquote>


 <p>The important question is:</p>


 <blockquote>

  <p><strong>"Why was it added?"</strong></p>

 </blockquote>



 <h2>Enter <code>git blame</code></h2>


 <p>This is where one of Git's oldest commands becomes surprisingly useful in AI-assisted development.</p>


 <pre><code>git blame path/to/file.js</code></pre>


 <p><code>git blame</code> shows which commit last changed each line, along with information about the author and commit.</p>


 <p>For example:</p>


 <pre><code>a91f4c21 John Doe 2025-11-18 42) const MAX_RETRIES = 7;</code></pre>


 <p>Now the agent knows that line 42 came from commit <code>a91f4c21</code>.</p>


 <p>That gives it somewhere to investigate next.</p>


 <pre><code>git show a91f4c21</code></pre>


 <p>The agent may discover:</p>


 <pre><code>Increase payment retries after gateway timeout incident


Payment provider occasionally returns temporary gateway errors

during high-volume periods.


Increase retries from 3 to 7.</code></pre>


 <p>Suddenly the "magic number" is no longer magic.</p>


 <p><strong>It has a history.</strong></p>



 <h2>But <code>git blame</code> Is Only the First Step</h2>


 <p>There is an important technical distinction here.</p>


 <p><code>git blame</code> answers:</p>


 <blockquote>

  <p><strong>"Which commit last changed this line?"</strong></p>

 </blockquote>


 <p><code>git log -L</code> can answer a deeper question:</p>


 <blockquote>

  <p><strong>"How did this particular line or function evolve over time?"</strong></p>

 </blockquote>


 <p>For example:</p>


 <pre><code>git log -L 42,48:src/services/payment.py -3</code></pre>


 <p>Or, when Git can identify the function:</p>


 <pre><code>git log -L :process_payment:src/services/payment.py</code></pre>


 <p>This can show the changes that shaped the relevant code instead of forcing the AI to scan the entire repository history.</p>


 <p>That distinction matters.</p>


 <p>A good AI coding agent should not blindly run thousands of Git commands before touching anything.</p>


 <p>It should investigate <strong>the history of the code it is actually about to change</strong>.</p>



 <h2>The Better AI Coding Workflow</h2>


 <p>Instead of:</p>


 <pre><code>Understand task

   ↓

Read code

   ↓

Change code

   ↓

Run tests

   ↓

Create PR</code></pre>


 <p>A production-conscious AI agent should work more like this:</p>


 <pre><code>Understand task

   ↓

Locate code

   ↓

Is this existing logic?

   ↓

   YES

   ↓

Inspect git blame

   ↓

Inspect relevant commit

   ↓

Trace line/function history with git log -L

   ↓

Identify intentional constraints

   ↓

Plan modification

   ↓

Change code

   ↓

Run tests

   ↓

Review diff

   ↓

Run relevant regression checks

   ↓

Create PR</code></pre>


 <p>That is a small change in workflow.</p>


 <p>But conceptually, it is huge.</p>


 <p>The agent is no longer treating the repository as merely a collection of files.</p>


 <p>It is treating it as a <strong>historical system</strong>.</p>



 <h2>The "History Before Refactor" Rule</h2>


 <p>If you build custom AI coding agents, this is a rule worth putting directly into the agent's instructions:</p>


 <pre><code>BEFORE modifying existing production code:


1. Identify the exact function, block, or lines being modified.


2. Use git blame to identify the commits that introduced or last

  changed the relevant lines.


3. Inspect the relevant commits with git show.


4. Use git log -L when the evolution of a function or line range

  needs deeper investigation.


5. Look for evidence of:

  - bug fixes

  - production incidents

  - race-condition fixes

  - API workarounds

  - rate-limit handling

  - browser-specific fixes

  - security fixes

  - backwards compatibility

  - performance workarounds

  - customer-impacting regressions


6. Do not remove or change an apparent constraint simply because

  it looks unnecessary.


7. If the historical reason is important, preserve the behavior

  and document the constraint.


8. Explain in the execution plan how the existing behavior will

  remain safe after the refactor.</code></pre>



 <h2>Why <code>git log -L</code> Beats Full Repository Scans</h2>


 <p>There is a tendency to solve AI coding problems by giving the model more files.</p>


 <p>"Read the whole repository."</p>


 <p>"Read every documentation file."</p>


 <p>"Read the entire GitHub issue."</p>


 <p>"Load the whole codebase into context."</p>


 <p>Sometimes that helps.</p>


 <p>But more context is not automatically better context.</p>


 <p>If an agent is modifying ten lines of a payment service, the most valuable information might be:</p>


 <ol>

  <li>The ten lines themselves.</li>

  <li>The commit that introduced them.</li>

  <li>The commit immediately before the change.</li>

  <li>The reason recorded in the commit message.</li>

  <li>The issue or incident associated with that commit.</li>

  <li>The tests that were added alongside the fix.</li>

 </ol>


 <p>That is <strong>surgical context</strong>.</p>


 <p>Git is particularly good at providing it.</p>



 <h2>Example: The Agent Investigates Before Refactoring</h2>


 <p>Imagine the agent is working on:</p>


 <pre><code>def process_payment(payload):

  max_retries = 7


  for attempt in range(max_retries):

    response = gateway.charge(payload)


    if response.ok:

      return response


    time.sleep(2)


  raise PaymentError("Payment failed")</code></pre>


 <p>A conventional refactoring agent might propose:</p>


 <pre><code>MAX_RETRIES = 3</code></pre>


 <p>and perhaps extract the retry mechanism into a generic utility.</p>


 <p>Looks cleaner.</p>


 <p>But before doing that, the agent runs:</p>


 <pre><code>git blame -L 42,48 src/services/payment.py</code></pre>


 <p>It discovers the relevant commit:</p>


 <pre><code>b4f19a0 Tech Lead 2026-02-11</code></pre>


 <p>Then:</p>


 <pre><code>git show b4f19a0</code></pre>


 <p>The commit message says:</p>


 <pre><code>Increase payment retries after gateway timeout incident


Gateway occasionally takes longer to recover during traffic spikes.

Keep seven attempts to avoid dropping delayed payment callbacks.</code></pre>


 <p>Now the correct engineering decision is obvious.</p>


 <p>The agent should not "clean up" the seven retries simply because three is more conventional.</p>


 <p>It should preserve the behavior.</p>


 <p>If the constraint is important enough, the code could become:</p>


 <pre><code># Seven retries are intentional. The payment gateway can temporarily

# delay responses during traffic spikes. See commit b4f19a0.

MAX_RETRIES = 7</code></pre>



 <h2>Why Green Tests Do Not Always Mean a Safe Refactor</h2>


 <p>One of the most dangerous assumptions in AI-assisted development is:</p>


 <blockquote>

  <p>"The tests passed, so the refactor is safe."</p>

 </blockquote>


 <p>Not necessarily.</p>


 <p>Tests answer questions about the behavior that you have encoded and exercised.</p>


 <p>They do not automatically capture:</p>


 <ul>

  <li>Undocumented operational constraints</li>

  <li>Production-only traffic patterns</li>

  <li>Third-party service behaviour</li>

  <li>Rare race conditions</li>

  <li>Browser-specific behaviour</li>

  <li>Infrastructure quirks</li>

  <li>Historical compatibility requirements</li>

  <li>Customer workflows nobody thought to write tests for</li>

  <li>Deployment-specific configuration</li>

  <li>Timing-sensitive failures</li>

 </ul>


 <p>This is especially relevant for small engineering teams.</p>


 <p>A Nigerian startup might have one developer maintaining the backend, another handling frontend work, and a founder occasionally jumping into the repository when something breaks.</p>


 <p>The test suite may be decent.</p>


 <p>But the company's real engineering knowledge may still live in people's heads.</p>


 <p>When those people are unavailable, Git history becomes extremely valuable.</p>



 <h2>Do Not Blindly Trust Commit Messages</h2>


 <p>There is another important caveat.</p>


 <p>Git history is not automatically correct.</p>


 <p>Developers write bad commit messages.</p>


 <p>Sometimes the message is:</p>


 <pre><code>fix bug</code></pre>


 <p>Or:</p>


 <pre><code>updates</code></pre>


 <p>Or:</p>


 <pre><code>final-final-fix</code></pre>


 <p>You cannot build a reliable AI engineering workflow around commit titles alone.</p>


 <p>The agent should correlate multiple signals:</p>


 <ul>

  <li><code>git blame</code></li>

  <li><code>git log -L</code></li>

  <li><code>git show</code></li>

  <li>Commit diffs</li>

  <li>Tests</li>

  <li>Issue references</li>

  <li>Documentation</li>

  <li>Comments</li>

  <li>Surrounding code</li>

  <li>Current runtime behaviour</li>

 </ul>


 <p>If the commit message says <code>cleanup payment service</code> but the diff contains a subtle retry change and a newly added regression test, the diff and test are much stronger evidence than the commit title.</p>



 <h2>When the Agent Should Investigate More Deeply</h2>


 <p>History-aware development should not turn into AI paralysis.</p>


 <p>The goal is not:</p>


 <blockquote>

  <p>"Never modify old code."</p>

 </blockquote>


 <p>That would be impractical.</p>


 <p>The goal is:</p>


 <blockquote>

  <p><strong>"Understand consequential old code before modifying it."</strong></p>

 </blockquote>


 <p>For example, extensive historical investigation may not be necessary for:</p>


 <ul>

  <li>Adding a completely new file</li>

  <li>Adding a new component</li>

  <li>Fixing a typo</li>

  <li>Formatting-only changes</li>

  <li>Updating documentation</li>

  <li>Changing an unused variable name</li>

  <li>Straightforward test additions</li>

  <li>Generated files</li>

 </ul>


 <p>The trigger should become stronger when the agent is:</p>


 <ul>

  <li>Deleting existing logic</li>

  <li>Changing retry behaviour</li>

  <li>Changing authentication logic</li>

  <li>Changing payment flows</li>

  <li>Changing database queries</li>

  <li>Changing asynchronous execution</li>

  <li>Changing caching</li>

  <li>Changing security checks</li>

  <li>Changing error handling</li>

  <li>Removing unusual workarounds</li>

  <li>Changing third-party integrations</li>

  <li>Changing production configuration</li>

 </ul>


 <p>These are the areas where historical context can have the highest value.</p>



 <h2>A Simple Rule: Strange Code Deserves an Explanation Before Deletion</h2>


 <p>One of the simplest instructions you can give an AI coding agent is:</p>


 <blockquote>

  <p><strong>If existing code looks unnecessarily complicated, investigate before simplifying it.</strong></p>

 </blockquote>


 <p>Not every ugly line is technical debt.</p>


 <p>Sometimes it is an encoded production lesson.</p>


 <p>Consider:</p>


 <pre><code>await new Promise(resolve =&gt; setTimeout(resolve, 50));</code></pre>


 <p>An AI sees an arbitrary 50ms delay.</p>


 <p>A human sees a suspicious 50ms delay.</p>


 <p>Neither should immediately delete it.</p>


 <p>The correct question is:</p>


 <blockquote>

  <p><strong>Why 50ms?</strong></p>

 </blockquote>


 <p>Run:</p>


 <pre><code>git blame path/to/file.js</code></pre>


 <p>Then:</p>


 <pre><code>git show &lt;commit&gt;</code></pre>


 <p>If the answer is:</p>


 <pre><code>Workaround for race condition in vendor SDK v2.3</code></pre>


 <p>you may have just prevented a regression.</p>



 <h2>This Changes How Developers Should Write Git Commits</h2>


 <p>There is a lesson here for human engineers too.</p>


 <p>If AI agents are going to use Git history as a source of engineering context, <strong>commit quality becomes part of your AI infrastructure.</strong></p>


 <p>Compare:</p>


 <pre><code>fix bug</code></pre>


 <p>with:</p>


 <pre><code>Keep 7 payment retries for delayed gateway responses


The gateway can temporarily return timeout responses during traffic

spikes. Reducing retries causes callbacks to be abandoned before the

provider recovers.


Related incident: PAY-309</code></pre>


 <p>The second commit is dramatically more valuable.</p>


 <p>Not just to humans.</p>


 <p><strong>To future AI agents.</strong></p>


 <p>A good commit message is effectively a small piece of machine-readable institutional memory.</p>



 <h2>Write Comments for Future Agents, Not Just Future Humans</h2>


 <p>There is also a case for strategic comments.</p>


 <p>Do not comment obvious code.</p>


 <p>This:</p>


 <pre><code># Set retries to 7

MAX_RETRIES = 7</code></pre>


 <p>adds almost nothing.</p>


 <p>But this:</p>


 <pre><code># Keep at 7: payment gateway may recover after transient timeout

# bursts. Lower values previously caused dropped callbacks.

# See commit b4f19a0.

MAX_RETRIES = 7</code></pre>


 <p>is useful.</p>


 <p>The comment explains <strong>why</strong>.</p>


 <p>That is the information an AI agent is least likely to infer from the code itself.</p>



 <h2>Git History Can Become an AI Memory Layer</h2>


 <p>This leads to a much bigger idea.</p>


 <p>We often talk about giving AI agents:</p>


 <ul>

  <li>Vector databases</li>

  <li>Documentation</li>

  <li>Embeddings</li>

  <li>Project instructions</li>

  <li>Memory files</li>

  <li>Issue trackers</li>

 </ul>


 <p>But one of the most valuable sources of project memory is already sitting inside most repositories:</p>


 <p><strong>Git history.</strong></p>


 <p>Every meaningful commit can potentially contain:</p>


 <ul>

  <li>What changed</li>

  <li>Who changed it</li>

  <li>When it changed</li>

  <li>Why it changed</li>

  <li>What problem it solved</li>

  <li>What code was affected</li>

  <li>What tests were introduced</li>

 </ul>


 <p>Git is not just a rollback mechanism.</p>


 <p>It is a chronological record of engineering decisions.</p>


 <p>An AI agent that knows how to interrogate that history can operate with considerably more context than an agent that only reads the current working tree.</p>



 <h2>What This Means for Cursor, Claude Code, Windsurf and GitHub Copilot Users</h2>


 <p>You do not need to abandon AI coding tools.</p>


 <p>You need to change how you instruct them.</p>


 <p>Instead of telling an agent:</p>


 <blockquote>

  <p>"Refactor this service and make it cleaner."</p>

 </blockquote>


 <p>Try something closer to:</p>


 <blockquote>

  <p>"Refactor this service. Before changing existing production logic, inspect Git history for the functions you intend to modify. Use git blame to identify relevant commits and git log -L to understand how critical sections evolved. Preserve intentional constraints and explain any historical behaviour that affects your refactor."</p>

 </blockquote>


 <p>That instruction is much more precise.</p>


 <p>You are not asking the model to magically become smarter.</p>


 <p>You are giving it a better engineering process.</p>



 <h2>A Production-Safe System Prompt for AI Coding Agents</h2>


 <pre><code>PRODUCTION CODE SAFETY RULE


Before modifying existing production code:


1. Identify the exact function, class, or line range being changed.


2. Determine whether the code predates the current task.


3. For existing logic, run:

  git blame -L &lt;start&gt;,&lt;end&gt; &lt;file&gt;


4. Inspect relevant commits:

  git show &lt;commit&gt;


5. If the reason for the code is unclear, trace its evolution:

  git log -L &lt;start&gt;,&lt;end&gt;:&lt;file&gt;


6. Look specifically for:

  - production incidents

  - regression fixes

  - race conditions

  - security fixes

  - API workarounds

  - rate-limit handling

  - compatibility requirements

  - database constraints

  - browser/device-specific fixes

  - performance workarounds

  - customer-impacting bugs


7. Do not remove behaviour solely because it appears redundant,

  outdated, unusual, or inconsistent with a preferred pattern.


8. Before refactoring, identify the invariant that the existing

  code is protecting.


9. Preserve that invariant in the new implementation.


10. If the historical reason is important and undocumented,

  add a concise comment explaining the constraint.


11. After modifying the code:

  - inspect git diff

  - run relevant tests

  - run regression tests where available

  - verify that the original behaviour remains intact


12. In the final report, explicitly state:

  - what historical context was discovered

  - which constraints were preserved

  - what tests were executed

  - what assumptions remain uncertain</code></pre>



 <h2>The Bigger Lesson: Faster Coding Needs Better Memory</h2>


 <p>AI has changed the bottleneck in software development.</p>


 <p>For years, one of the biggest problems was:</p>


 <blockquote>

  <p><strong>How quickly can we write the code?</strong></p>

 </blockquote>


 <p>AI is dramatically improving that.</p>


 <p>The next question is:</p>


 <blockquote>

  <p><strong>How safely can we change the code?</strong></p>

 </blockquote>


 <p>That is different.</p>


 <p>When a developer spends three hours implementing a feature, they naturally build some understanding of the surrounding system.</p>


 <p>An AI agent can make a similar change in minutes.</p>


 <p>That speed is useful.</p>


 <p>But it means the development process needs stronger guardrails.</p>


 <p>Git history is one of those guardrails.</p>


 <p>Not because Git is intelligent.</p>


 <p>Because Git remembers.</p>



 <h2>Do Not Make Your AI Agent Afraid of Legacy Code</h2>


 <p>There is a temptation to go too far with this idea.</p>


 <p>You might instruct your agent:</p>


 <blockquote>

  <p>"Never modify code written by someone else."</p>

 </blockquote>


 <p>That solves the problem by creating another problem.</p>


 <p>Legacy code has to be changed.</p>


 <p>Old workarounds eventually become unnecessary. Dependencies get upgraded. Architecture evolves. Security requirements change.</p>


 <p>The correct principle is not:</p>


 <blockquote>

  <p><strong>"Legacy code is sacred."</strong></p>

 </blockquote>


 <p>It is:</p>


 <blockquote>

  <p><strong>"Legacy code is evidence."</strong></p>

 </blockquote>


 <p>Investigate it before replacing it.</p>


 <p>If the historical reason is still valid, preserve it.</p>


 <p>If the historical reason is obsolete, remove it deliberately.</p>


 <p>If nobody knows why it exists, increase your testing and investigation before touching it.</p>


 <p>That is engineering judgment.</p>



 <h2>AI Refactoring Checklist</h2>


 <p>Before approving an AI-generated production refactor, ask:</p>


 <ul>

  <li>Did the agent identify the exact code being changed?</li>

  <li>Did it inspect <code>git blame</code> for important existing lines?</li>

  <li>Did it inspect the relevant commits?</li>

  <li>Did it use <code>git log -L</code> when the evolution was unclear?</li>

  <li>Did it look for regression fixes?</li>

  <li>Did it look for production incidents?</li>

  <li>Did it check related tests?</li>

  <li>Did it preserve intentional timing, retry, caching, security, or compatibility behaviour?</li>

  <li>Did it inspect the final <code>git diff</code>?</li>

  <li>Did the relevant tests pass?</li>

  <li>Did the agent explain why the refactor is safe?</li>

 </ul>


 <p>If the answer to these questions is yes, you have substantially improved the quality gate around AI-generated code.</p>



 <h2>Final Takeaway</h2>


 <p>AI coding agents are becoming powerful enough to modify real production systems at remarkable speed.</p>


 <p>That is an opportunity.</p>


 <p>But speed without historical context can create a new class of engineering failures:</p>


 <blockquote>

  <p><strong>Confident refactors that are technically reasonable but operationally wrong.</strong></p>

 </blockquote>


 <p>The solution is not to stop using AI.</p>


 <p>It is to make AI behave more like an experienced engineer.</p>


 <p>Before changing important existing code:</p>


 <pre><code>git blame</code></pre>


 <p>to find out which commit changed it.</p>


 <p>Then:</p>


 <pre><code>git show &lt;commit&gt;</code></pre>


 <p>to understand what that change did.</p>


 <p>And when you need to understand how a function or line range evolved:</p>


 <pre><code>git log -L</code></pre>


 <p>to trace its history.</p>


 <p>The most important question an AI coding agent can ask before rewriting legacy code is not:</p>


 <blockquote>

  <p>"Can I make this cleaner?"</p>

 </blockquote>


 <p>It is:</p>


 <blockquote>

  <p><strong>"Why was this written this way in the first place?"</strong></p>

 </blockquote>


 <p>Because sometimes the ugliest line in the repository is not technical debt.</p>


 <p>Sometimes it is the scar left by the last production incident.</p>


 <p>And if your AI agent learns to read those scars before touching the code, you give it something every good engineer needs:</p>


 <p><strong>Institutional memory.</strong></p>
